# Step 05 — shared account state

Implemented and verified on 12 September 2026. This closes RW-01 and the account/child-goal sharing portions of RW-05 and UI-06. General screen lifecycle demand remains step 09; ancillary startup work remains step 10.

## Changes

[FirebaseAuthRepositoryImpl](../../core/data/src/main/java/com/mantrasiddhi/data/remote/FirebaseAuthRepositoryImpl.kt) now owns one Firebase auth listener in a process-scoped coroutine lifetime. [AccountStateProducer](../../core/data/src/main/java/com/mantrasiddhi/data/remote/AccountStateProducer.kt) shares the resolved profile, rather than merely sharing the raw auth callback. Subscribers and short `first()` reads reuse that result. Opt-in probes count listener attachment/detachment, account loads, profile gets and explicit refresh operations without account IDs or payloads.

[AccountResolution](../../core/domain/src/main/kotlin/com/mantrasiddhi/domain/model/AccountResolution.kt) distinguishes unresolved identity, signed out and a resolved account. The compatibility account stream emits null while unresolved so account-dependent UI clears; startup routing uses the explicit resolution state and does not mistake that null for sign-out. UID changes immediately replace replay, cancel in-flight work and advance a request generation. Generation and current-Firebase-UID checks reject late results, including A → B → A. A canceled caller does not cancel a refresh shared by other callers. Recoverable failures remain retryable.

Concurrent explicit refreshes share one operation. A deliberate server recovery cannot be satisfied by a cache-capable startup read: if they overlap, one server recovery follows the shared startup read. Later explicit refreshes still fetch again. Google refresh retains its profile/identity repair transaction and post-write profile read. Interactive sign-in, signup, Google linking and child setup own their auth callback interval and publish their completed profile, avoiding a competing listener load or a second publication-triggered reload. Existing server role checks, offline fallback scoped to the same UID, Google recovery and child PIN gates remain intact.

[MainViewModel](../../frontend/android/src/main/java/com/mantrasiddhi/presentation/MainViewModel.kt) routes unresolved startup explicitly, cancels superseded profile opening, and guards delayed retries across account changes. Name/photo changes do not repeat startup profile association. Refresh publication and the retry response share profile opening. Confirmed signed-out startup still leaves interactive sign-in/import choices to the auth screen.

[IncrementActiveCloudGoalUseCase](../../core/domain/src/main/kotlin/com/mantrasiddhi/domain/usecase/GoalCloudUseCases.kt) reads the shared account to check the role and requires the Firebase UID captured with the recitation's local profile. The repository rechecks that UID and passes it explicitly to the outbox; it cannot enqueue against a newly signed-in child. Twenty eligible attempts still request twenty updates. The durable save/outbox atomicity gap is unchanged and remains step 06.

[SharedChildGoals](../../core/data/src/main/java/com/mantrasiddhi/data/remote/SharedChildGoals.kt) shares the current child's Firestore snapshot mapping/sorting between Main notifications and Family. It keys switching by child UID, rejects another UID's replay, and releases the source and replay when the last consumer leaves. There is no synthetic empty initial child snapshot, since that would incorrectly establish the notification baseline before existing goals arrive. Main keeps its original first-snapshot baseline and already-seen goal IDs across metadata updates and Family navigation; it resets when account/role changes. Its existing notification lifetime is retained.

[FamilyViewModel](../../frontend/android/src/main/java/com/mantrasiddhi/presentation/screens/family/FamilyViewModel.kt) uses one account collector with one cancellable group of account-dependent queries. Identity/role changes clear account data and selection; name/photo changes update identity without restarting queries. Result ownership checks also protect selected-child goals. A section error cannot terminate account observation and strand the previous account's state. This does not make Family's lifetime visibility-aware; that remains step 09.

## Verification

- **586 unit tests passed:** 363 domain, 125 data and 98 app; zero failures, errors or skips. New coverage includes shared producer counts; concurrent and subsequent refreshes; refresh during startup; cancellation and late results; A → B → A; failed refresh/interactive setup; Google linking publication; saved-owner/outbox guards; startup recovery, child setup and interactive routing; queued/late retries; notification baselines; and Family metadata/role/error handling.
- **Repository work counts:** the real Firebase repository with mocked SDK tasks attaches one listener and calls the profile `get()` once for seven account subscribers plus twenty correct-attempt use-case calls. All twenty child-goal update requests are retained, with no server refresh for the role checks. Seven concurrent refresh callers share one operation; a later explicit refresh starts another.
- **Child-goal counts:** Main and Family consumers share one source. Metadata changes and removing Family do not restart it while Main remains; removing the last consumer leaves zero active sources and clears replay. Account replacement cancels the old source, and a new child receives no old-child replay or placeholder baseline.
- **Three physical-device tests passed** on Pixel 7 Pro: [AccountSharingDeviceTest](../../core/data/src/androidTest/java/com/mantrasiddhi/data/remote/AccountSharingDeviceTest.kt) runs the production producers on Android Main/Default dispatchers with disposable in-memory accounts/goals. It checks seven subscribers/twenty reads, concurrent refreshes, replacement during resolution, child-setup state, shared goal work and cleanup. No real account sign-outs, role changes or artificial chants are performed.
- **Real-app probe check:** the final optimized benchmark APK opened usable Home, entered Family and returned through the launcher after backgrounding. All three snapshots came from the same process and each reported `auth.listener.attach = 1`, `auth.loadAccount = 1`, and `auth.profile.get = 1`. The final APK hash and raw snapshots are retained in [step-05-results.json](step-05-results.json). This was one existing signed-in account, not a controlled child-account or timing benchmark. The baseline had three active account producers after Home/Progress/Settings; its journey differs, so no timing or billed-read improvement is inferred.
- **Build and lint:** debug app, data instrumentation APK and optimized benchmark app build successfully. Lint has zero errors, 14 warnings and three hints. An initial benchmark KSP generated-file deletion failure on Windows passed when retried separately. `git diff --check` passed.

Local logs: `build/perf-05-final-verification.log`, `build/perf-05-device-tests.log`, `build/perf-05-startup-counters.txt`, `build/perf-05-family-counters.txt`, `build/perf-05-resume-counters.txt`, plus standard Gradle XML/lint reports. The normal debug APK was reinstalled after measurement.

## Limits

These checks establish sharing, cancellation, ownership and baseline behavior. They do not close transactional count delivery (06), remote discovery/retry (07), visibility-based producer demand (09), splash/reminder startup work (10/11), real two-device recovery or the full performance audit (13). Explicit Google recovery may still require multiple different reads/writes within its one coalesced operation. No Firestore rules, cloud data schema or account contents were changed by this implementation.

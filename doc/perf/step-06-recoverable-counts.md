# Step 06 — recoverable session projections

Implemented on 12 September 2026. This addresses DB-02 and DB-07. Production rules deployment is a separate release step; no production account or projection was modified during verification.

## Counting contract

[RecitationRepositoryImpl](../../core/data/src/main/java/com/mantrasiddhi/data/repository/RecitationRepositoryImpl.kt) commits the assessment, accepted-audio ledger contribution, local goal projections and the compound `PRACTICE_RECORD` outbox event in one Room transaction. The event includes stable session identity, the owning Firebase UID, occurrence time, occurrence date/timezone and captured child eligibility. It is both the history upload and the durable instruction to update summary/assigned-goal counts. There is no second independently queued delta.

Room v16 adds nullable occurrence/eligibility fields without inventing metadata for older rows. It also marks existing backup accounts for recovery so an otherwise settled account receives its one-time projection repair. Stable-ID save retries retain the original metadata and do not enqueue or credit again. Failure before commit rolls back every component; scheduler/ViewModel cancellation after commit leaves recoverable work.

[SessionProjectionSync](../../core/data/src/main/java/com/mantrasiddhi/data/sync/SessionProjectionSync.kt) atomically creates the canonical session, publishes its restore-feed record, advances the compact summary and credits at most one eligible assigned goal. The canonical session's existence is the receipt across devices, installations and outbox stream changes. Replaying a committed session never increments again or redirects its reward to a later goal. Stream checkpoints only govern pending UI state; they are not the counting identity.

Every attempt, including failed and PRACTICE attempts, contributes its actual score to session analytics. Only correct NORMAL audio with captured child eligibility earns a parent reward. Manual japa and its corrections remain in the editable ledger and never earn audio rewards. Eligible goals must have existed at the original occurrence time; selection is oldest eligible unfinished goal, with stable goal-ID ties, and counts are capped. New sessions preserve their original role/date inputs even if account state, midnight or timezone changes before upload.

The former post-save summary call and ViewModel reward coroutine are removed. Anonymous summary/reward APIs now return an explicit failure and are deprecated. Pending historical anonymous outbox events are retired; canonical repair replaces their effects. The existing local save/capture safeguards remain intact for step 08.

## Bootstrap and historical repair

Bootstrap is versioned by `sessionProjectionVersion = 2`. Before scanning, the client persists a cutover barrier. The new rules then require canonical session creation to advance the summary in the same transaction and reject old anonymous summary writes. The scan reads canonical cloud sessions in 200-record pages, rather than treating one device's partial local history as a seed. It calculates actual daily attempt counts, correct counts, score sums, lifetime totals and best score. The rolling daily-key cap does not truncate lifetime totals.

The scan's commit checks the progress revision/account role and rereads the selected goal documents. A competing commit causes a rescan rather than a stale overwrite. Android can surface a rules denial before reporting an optimistic transaction conflict; delivery makes at most three outer transaction attempts, and only retries that denial when a server read proves the projection revision changed. Unresolved contention or actual permission failures retain the durable event for the coordinator's later retry.

Historical assigned goals are rebuilt from the same canonical sessions, ordered by occurrence time and stable session ID, using goal creation times and target caps. Their previous counts do not act as anonymous extra credit. The pre-repair summary and goal documents are atomically retained in owner-private, immutable `users/{uid}/projectionRepairs/v2_progress` and `v2_goal_{goalId}` archives. Repair and its archives commit together; rerunning a successful bootstrap does not overwrite them or rebuild the seed. A process cache avoids even the bootstrap reads during subsequent deliveries.

Malformed canonical sessions are excluded from the projection and counted in `projectionInvalidRecords`; the existing backup admission/quarantine path retains and reports the invalid source. An incomplete bootstrap is retried, so repairing that historical source can correct the projection once. A complete bootstrap is not scanned on every attempt. While session receipts remain unacknowledged, the current user's progress repository falls back to Room instead of adding a pending event that might already be covered by bootstrap.

## Compatibility and release limits

- **Deploy the updated Firestore rules before distributing or installing this build against production.** The deployed step-02 rules do not accept the new session metadata or repair archives. New rules allow legacy writes before an account's cutover; afterward, older clients retain rejected work locally and must upgrade to upload it. This prevents old anonymous increments from corrupting a repaired summary. The production app installed on the test phone was left unchanged.
- Counts reconstructed by repair represent available valid canonical sessions. Historical sessions that were never backed up and no longer exist on any device cannot be inferred from a summary. Upgrade/sync other devices to contribute their surviving source records. Original projections remain archived for inspection instead of being discarded.
- Legacy accepted audio uses the canonical ledger's recorded date when available. Other legacy sessions lack an original timezone; they use a documented deterministic UTC fallback. New sessions always retain their exact occurrence date. Historical eligibility without captured metadata uses the account's stored CHILD role plus correct NORMAL mode; the app has no historical role-change log.
- Bootstrap repairs up to 200 assigned goals atomically, including their archives. Larger accounts fail visibly and retain work for a dedicated server migration; this avoids exceeding Firestore's transaction write limit. Normal Firestore document/request size limits still apply. No production-size or billed-read improvement is claimed.
- Source assessments remain immutable under step 03. Manual corrections, stale edits and allocation rules remain covered by the existing ledger tests. A deliberate administrative rewrite of already-counted immutable source records after a completed cutover is not an automatic continuous reconciliation feature.
- Remote-only discovery and pre-claim retry behavior remain step 07. These tests use one physical phone with isolated Room replicas and local Firebase emulators; a real two-phone/offline production scenario remains step 13.

## Verification

- **590 unit tests:** 363 domain, 129 data and 98 app; zero failures/errors/skips. New pure-policy coverage checks exact daily aggregation, failed/practice attempts, captured versus legacy eligibility, date fallback, goal creation-time/tie/cap behavior and daily retention. Existing counting, ownership and account isolation tests remain green.

A second instrumentation process recovers the session, ledger and compound event, then retries the save without creating another event. `Process crashed` is the expected first-phase result; the recovery phase passes.

- **60 backend tests passed:** rules regressions include atomic session/summary publication after cutover, legacy compatibility before cutover, prevention of summary downgrade/anonymous increments, occurrence metadata validation and private immutable repair archives.
